## 处理原则

优先复用现有有界读取、CodeMirror、Reka UI 与 diff 的预算接口。保留既定字体作用域、补全键位和轻量候选范围；不做整仓拆分或未来功能插件化。真正的进程停止失败仍须保留可重试状态，不把尚存活的进程当作已释放。macOS 没有实机，仅记录静态、键位、签名与资源核验。

## M1 资源与清理修复

- 编辑器与辅助文件复用读取中有界的 8 MiB 预算，压缩包及配置入口采用 100 MiB 预算；目录快照按实际读取字节累计。文件增长不能绕过单文件读取上限。
- Diff 使用现有 diff 库的 50/25 ms 及编辑距离预算；超出时按行或显示明确的限长预览，保留原始输入与判定结果。困难样本在本机约 57 ms 返回。
- 编译与评测的清理步骤独立执行；保留原始错误、成功/失败判定，并记录清理警告。缓存释放与文件关闭也保留原始错误。停止真实进程失败仍按可重试状态处理。
- 构建与 41 项相关核心回归通过；Linux 与 Windows 成品均通过相同 6 项资源、保存及文本编码流程。Windows EXE 的 ASAR 完整性字段与程序文件按远端哈希核对。

故障测试使用 syncBuiltinESMExports 同步 Node 的原生 ESM 绑定，确保注入真正作用于生产调用；Diff 夹具按“查看原文”切回后核对输出末尾。两处夹具修正保留了原有故障和完整性断言。

所有自定义模态窗口都使用 DialogActions；原生提示共用 nativeButtonOrder，保留动作语义及安全默认项。探针核对保存、编译、重启、外部修改和删除五类原生参数，并在设置、新建、构建和导出窗口检查焦点及 Escape。未发现绕过公共动作组件的确认窗口；新建名称改用 Reka 的焦点事件，修复 autofocus 被首个选择框抢占的问题。

补全在亮暗主题核对前三项、选中态及长签名截断，继续采用 CodeMirror 的现有规则。16 档缩放实测发现窄窗口动作组不换行、极矮视口裁切设置入口，修正所属布局规则后通过。1280×720 窗口与中英字号 8/40、40/8 组合保持代码字体和 UI 字体分离。

扩大故障检查后，测试点更新事务也复现了清理错误掩盖写入失败；现保留 ENOSPC、原规则及后续重试能力。完整回归还发现本轮清理辅助函数把 Promise 值作为参数传给 proper-lockfile 的释放函数，已改为零参数调用并补断言；格式化保留同一文档编辑后的提示，跨文档迟到结果继续失效。

## M4 扩大 Windows 实测后发现的保存边界

原生成品全流程出现原子重命名的 EPERM：一次发生于调试启动前的项目元数据写入，一次使源码保存保留未保存标记。现将所有 write-file-atomic 调用收进 core/atomic-file.ts，继续使用原库的同步、权限与原子替换机制；只对 Windows 的 rename + EPERM/EACCES/EBUSY 最多重试四次，等待合计 750 ms。整次保存含重试共用按文件队列，失败不会毒化下一次保存，也不删除或改权限来绕过失败。

错误类别参考 [VS Code 文件系统实现](https://github.com/microsoft/vscode/blob/main/src/vs/platform/files/node/diskFileSystemProvider.ts)。本机具体占用进程未定位。三个核心故障用例验证顺序、持续失败、原字节、临时文件回收及后续重试；完整核心 178/178 通过。Windows 成品直接注入 fs.rename 错误，并与原失败场景一起通过四项回归。

另一处 Windows 夹具在首次规则文件创建前就读取文件，已改为仅在 ENOENT 时继续等候；内容及原源码保持断言不变。
